## Executive Summary

Anthropic's September 2, 2026 blog post, "A guide to the anatomy of effective commerce agents," distills a year of building commerce agents on Claude with retailers, marketplaces, travel, entertainment, and telecom companies. The finding is blunt: every effective commerce agent in production shares the same skeleton — a single agent loop equipped with skills and tools, not a fleet of domain-specific subagents and not an intent router. Latency and cost are won through caching design; safety is enforced in the harness, not the prompt.

## Architecture: Why Skills Beat Subagents

Anthropic defines a commerce agent as one that simplifies buying and selling across an online catalog — covering both consumer-facing agents (search, compare, substitute, assemble an order) and business-facing agents (answer sales questions, run promotions, manage inventory and pricing). The core is a single model in a standard agent loop, with no intent router segmenting the conversation up front and no set of domain-specific agents behind it.

A subagent-per-domain design looks natural but underperforms in practice, Anthropic argues, because a commerce conversation is one tightly coupled session spanning multiple intents and turns that requires considerable shared context. In a subagent architecture the orchestrator holds the cart, the user's preferences, and the conversation history, and every handoff to a subagent is a state-lossy operation that degrades response quality and can cost several times the tokens and add seconds of latency.

Instead, Anthropic recommends skills: skill instructions load into the main agent that already holds the entire conversation history, giving per-domain modularity and context control without the handoff tax. Across several enterprise comparisons, a single agent with skills consistently outperformed both the one-prompt-for-everything design and the subagent design on quality — often at lower cost and latency too. The exception is when the orchestrator calls a subagent as a tool for a narrow, self-contained task warranting its own dedicated context window — a deep-research subagent that searches, reads documents, runs code, and returns only a compact answer, or a genuine "hand-off" to a domain that already runs its own purpose-built, compliance-bearing agent (pharmacy, financial services), where the domain agent becomes the user's counterpart rather than being bounced in and out within a turn.

Whether an instruction belongs in the system prompt or a skill is decided by frequency: anything touching a third or more of traffic goes in the system prompt; the rest goes in skills. Safety and legal rules, brand constraints, and critical user facts (like allergies) always live in the system prompt. In Anthropic's reference implementation, the shopping agent's prompt holds grounding, cart/checkout semantics, and presentation rules, while five skills — search-discovery, purchase-research, planning-goals, customer-care, and memory-personalization — carry the long tail.

## Winning Latency and Cost Through Caching

Anthropic's own measurements show that what consistently moves retention, engagement, and cart size on agentic surfaces is whether the task was actually completed and the answer relevant — not marginal latency gains. Even so, latency should be attacked on two fronts: end-to-end and perceived. End-to-end latency comes down to three levers minimized in sum — fewer turns (load likely context up front, use a smarter model, call independent tools in parallel), faster tools (optimize the backend, dispatch tool calls eagerly as arguments complete), and faster tokens. Perceived latency drops by streaming presentation components as they form and by showing short, plain-language progress lines (e.g., "finding hotels near the water") while the agent gathers context.

Prompt caching is called out as the single largest cost-reduction lever. Cached input token reads cost a tenth of fresh ones; cache writes carry roughly a 1.25x premium, but a cached prefix pays for itself on its second use. The best commerce deployments Anthropic has seen run 90–99% cache hit rates, with cached reads roughly 1.5–2x faster at around 100k tokens. Because caching is prefix-based, a request should be ordered into three segments by how often they change: global (system prompt and tool definitions, identical across every session), session (per-user context and conversation history), and volatile (anything that changes within a session, like the current time or page) — placed last. The most common mistake, per Anthropic, is putting a timestamp or the current page at the top of the system prompt, which silently breaks the cache on every request.

Model choice is also settled by measurement, not intuition: Anthropic recommends starting a sweep with Opus for merchant agents (analysis-heavy tasks) and Sonnet for consumer agents (where latency weighs more), but insists on measuring cost per completed task rather than per model call — a cheaper model that needs more turns or fails more often isn't actually cheaper.

## Three Pillars That Get an Agent Through Production: Memory, Safety, and Evals

Long-term memory "belongs in your systems, not in the model." A flat markdown profile works at small scale, but most production commerce agents outgrow it; the practical replacement is the database a company already operates, storing each fact as a small typed record (key, value, category, source session). Writes should happen asynchronously, outside the user-facing turn — Anthropic reports this achieved 13% higher fact recall on its internal commerce memory eval suite compared with a tool the agent calls mid-conversation. Reads happen in three layers: a small fixed set always in context, facts pre-fetched per turn from signals that also pre-load a skill, and everything else behind a lookup tool.

On safety, the post draws a hard line: "the prompt is where safe behavior starts, but in commerce it can't be where safety is enforced," because failures are financial and often irreversible, and a prompt rule is one injection or one bad sample away from being skipped. Every action that moves money or changes the business — order placement, payments, refunds, price changes, campaign launches — ends in an action the harness controls, not the model. On the consumer side, the backend interface the agent calls has no charge method at all; on the merchant side, every write produces a server-issued, staged change ID, and `apply_change` only succeeds for IDs approved through a real surface. Writes and renders accept only server-issued IDs — a hallucinated ID, a user-pasted ID, or one planted in a review is refused before the backend ever sees it. Caps on transactions are checked against the resulting state after the write, not the request, and cart writes for one session are serialized so parallel tool calls can't combine to exceed a limit.

On evals, the core rule is "evaluate snapshots, not conversations." Because the model's API is stateless, any state a commerce conversation can reach can be constructed directly — build the test state, append the test user message, run the agent from there, then grade the final state and rendered response. Simulated-user evals, where a second model plays the user and a judge grades the whole conversation, are called a poor measurement tool, useful mainly for finding coverage gaps. Anthropic stresses writing a negative case for every positive one, embedding failure preconditions (a busy first turn, an earlier contradiction) rather than starting cases from a clean state, and partnering with subject-matter experts — 50–100 eval cases per user flow is offered as a reasonable starting point.
