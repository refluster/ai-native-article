## Executive Summary

As Claude-driven code generation and PR review accelerated, Anthropic's CI job volume grew 25x in six months, repeatedly overwhelming its test-impact-analysis service. Three successive patches bought only 70 days, then 29 days, then less than a day before the team redesigned the service around a stateless, journal-based architecture. Writing on Claude's blog (September 14, 2026), author Sachin Malhotra distills the lesson to one line: always plan for the exponential.

## Background: A PR Surge in the Agentic Era

Anthropic engineers now ship roughly 8x as much code per quarter as they did between 2021 and 2025. Claude authors 80% of that code and also plays a large role in reviewing and approving pull requests. With writing code no longer the constraint, pressure shifted to CI. At the same time, the number of tests across the codebase grew 10x while headcount grew only nominally — together driving a 25x increase in CI jobs over six months (not every test runs on every PR, the author notes, so the math isn't a flat multiplication).

## How the Test-Impact-Analysis Service Worked

Anthropic built a deterministic test-impact-analysis (test-selection) service that decides which tests to run on a given change, based on past test performance and package relevance. It rests on two components staying in sync:

- **A "listener"** records test results from every CI run.
- **A "selector"** reads that result history and decides which tests run on each open PR.
With multiple CI jobs firing every second, the listener began falling behind the PR queue — and in an AI-native SDLC, even a 20-minute lag could leave tens of thousands of test updates unapplied. A bad merge triggered unnecessary investigations across the board; a flaking dependency started blocking merges; a newly fixed or added test wouldn't run until the listener caught up, risking a regression. Because the original (v0) design kept a running per-test history behind a single writer, the service could not be horizontally sharded.

## Three Patches, Three Limits

By last October the service was already straining, and the team got paged two days straight.

- **Patch 1 — a bigger machine.** Doubling the service's cores was easy, and known to be temporary; it lasted about 70 days.
- **Patch 2 — sharding (February).** The team realized the listener didn't need one writer for the whole service, only one writer per package, so it split each package's state onto its own worker. Claude generated the sharding code; the author ran a long-lived session in an internal build of Claude Tag that paged him whenever listener lag exceeded 50,000 jobs. This patch lasted 29 days.
- **Patch 3 — daily restarts (March).** The process began hitting its memory limit by mid-afternoon most weekdays. The team found only four bugs; swapping the memory allocator did nothing, and profiling the already-overloaded singleton in production was judged too risky, so daily restarts became the fallback — buying less than a day of headroom. Falling more than an hour behind, which happened repeatedly, meant the listener missed results outright, leaving the test-selection component working from stale data and running tests that were already flaky or broadly failing. The author is explicit that this never meant CI skipped running, or that untested code reached production — only that the selector's picture went stale.
## The Redesign: Going Stateless with a Journal

The team finally redesigned the service, taking Claude's advice to give test selection a database — an in-memory data store — offloading the bulk of in-memory processing the old singleton had carried. In the new design, any listener worker can process any result and append it to a journal without holding state, making the fleet stateless and horizontally scalable; a small separate consumer process rolls the journal up into per-test history every few seconds, which the selector then queries quickly. The distributed architecture costs more to run but is far easier to scale and memory-profile than a shaky singleton. One engineer built it in three weeks — a project that, a year earlier, would have taken closer to a quarter. After cutover, the hourly-max backlog of unprocessed job-result events went from building up week over week to flat; Claude handled much of the journal-sizing and worker-count tuning autonomously.

## The Lessons

Asked what he'd do differently if sent back to October 2025, the author names three things. First, account for the AI exponential: CI jobs grow exponentially as the average number of agents per engineer rises and PR approval automation improves — reinforced by Claude's preference for smaller, more granular PRs, which itself adds daily CI volume. His advice to other engineering teams: assume your architecture will face 25x load within two quarters, and where budget allows, design v0 for 10–20x your perceived scale. Second, instrument services to act as Claude's eyes and ears, so it can hill-climb and fix problems incrementally faster than a human could alone. Third, keep state out of the process from the start, and avoid running any critical service as a single, unmeasured instance — CI, he concludes, is evolving too fast to proceed any other way.
