## Codex “Locked computer use” Operating Conditions and Safety Constraints

## Executive Summary

The Codex app’s “Locked computer use” is a mechanism that allows Codex to continue using Computer Use even after a Mac has been locked, if the feature has been enabled in advance. However, this is not a general-purpose remote unlock feature; it is limited to brief automatic unlocks tied only to an “active, trusted computer use turn.”

While this feature integrates an Apple authorization plug-in into the macOS unlock flow, it is designed around constrained operating assumptions, including blocking local use, covering all displays, and relocking if local input is detected.

## Prerequisites and Scope of Computer Use

The Codex app’s Computer Use is described as a capability that lets Codex “see and operate” the graphical user interface on macOS. The source makes clear that it is intended for situations where the command line or structured integrations are insufficient.

- Evidence
- Computer Use is “currently available on macOS”.
- However, at launch it is available “except in the European Economic Area, the United Kingdom, and Switzerland at launch”.
- Using it requires installing the Computer Use plugin.
- If prompted by macOS, you must grant “Screen Recording” and “Accessibility” permissions.
- The role of those permissions is explicitly stated: Screen Recording is “so Codex can see the target app”, and Accessibility is “so Codex can click, type, and navigate”.
- Implications
- The feature’s operating requirements are not just in-app settings; they also include granting OS-level permissions in macOS.
- Codex is designed to interact with the GUI visually, and both understanding the state of the target app and operating it depend on Screen Recording / Accessibility.
- Because both the supported regions and the OS are limited, any workflow that assumes Computer Use is environment-dependent.
## Which Tasks Should Use Computer Use

The source says Computer Use should be used only for GUI-dependent work. In particular, it presents tasks that are difficult to verify through files or command output alone as good fits.

- Evidence
- The following are listed as suitable use cases.
- “Testing a macOS app, an iOS simulator flow, or another desktop app that Codex is building”
- “Performing a task that requires your web browser”
- “Reproducing a bug that only appears in a graphical interface”
- “Changing app settings that require clicking through a UI”
- “Inspecting information in an app or data source that isn’t available through a plugin”
- “Running a scoped task in the background while you keep working elsewhere”
- “Executing a workflow that spans more than one app”
- For a locally built web app, the guidance is to “use the in-app browser first”.
- If the target app has a dedicated plugin or MCP server, you should “prefer that structured integration for data access and repeatable operations”.
- To start Computer Use, “Mention @Computer or @AppName in your prompt, or ask Codex to use computer use”.
- The example given is “Open @Chrome and verify the checkout page still works after the latest changes.”
- Implications
- Computer Use is not the first choice; it is positioned as a fallback when a structured plugin / MCP server or the in-app browser cannot adequately substitute.
- It is best suited to tasks like visual verification, cross-app workflows, browser interaction, and reproducing GUI-specific bugs—cases where a CLI lacks sufficient observability or reproducibility.
- The prompt design expects you to specify the target app or flow explicitly, with the assumption that scope will be kept narrow.
## Approval Model: macOS Permissions and Codex App Approvals Are Managed Separately

The source separates OS permissions from approvals inside Codex. The ability to see and operate apps is managed at a different layer from the question of which apps Codex is allowed to use.

- Evidence
- “The macOS system permissions for computer use are separate from app approvals in Codex.”
- macOS permissions “let Codex see and operate apps”.
- App approvals “determine which apps you allow Codex to use”.
- “File reads, file edits, and shell commands still follow the sandbox and approval settings for the thread.”
- During a task, Codex “asks for your permission before it can use an app on your computer”.
- Users can select “Always allow”, making future use of the same app not require reapproval.
- The “Always allow list” can be removed from the Computer Use section in Codex settings.
- In addition, “Codex may also ask for permission before taking sensitive or disruptive actions”.
- If it cannot control an app, users are told to check the Codex app’s “Screen Recording and Accessibility” in “System Settings > Privacy & Security”.
- Implications
- Granting Screen Recording / Accessibility alone does not mean Codex can freely handle any app it wants.
- Approvals are accumulated on a per-app basis, and while “Always allow” increases the level of automation possible in future tasks, it also broadens the potential impact of misuse.
- File editing and shell execution still remain subject to sandboxing and thread-level approval, so GUI operations are not being elevated into a wholly privileged path.
## How Locked computer use Works and Its Constraints

Locked computer use is defined as a feature that allows Computer Use to continue from a connected device after a Mac has been locked. The source explicitly says the unlock path is tightly constrained and is not a general-purpose means of unlocking the machine.

- Evidence
- “Locked computer use lets Codex use Computer Use after your Mac locks, but only after you enable it.”
- Its use case is “when a Codex task needs to use desktop apps from a connected device after the Mac locks”.
- When enabled, Codex installs “an Apple authorization plug-in that participates in the macOS unlock flow”.
- It explicitly states: “It’s not a general-purpose remote-unlock path for your Mac, and it doesn’t let other apps or local processes unlock the computer.”
- The setup flow is as follows.
- “Open Codex settings > Computer Use”
- “Enable locked computer use”
- “Start a task that uses computer use from a connected device after your Mac’s screen has locked”
- When a Codex task accesses an app through Computer Use after the machine is locked, Codex “temporarily unlocks the Mac while blocking local use and preserving the locked screen protections”.
- Before unlocking, it verifies “whether the unlock attempt is for an active, trusted computer use turn”.
- Outside those brief conditions, “Codex denies the unlock and asks you to unlock manually if needed”.
- Implications
- Locked computer use is a narrowly scoped feature intended to “allow a task to continue after the Mac is locked,” not for remote administration or unrestricted remote wake-and-resume.
- The decision to allow unlocking is tied to an “active, trusted computer use turn”, making it fundamentally different from a permanently available backdoor-style feature.
- It assumes continued use from a “connected device”, meaning the Codex execution context itself must still be active.
## Safeguards in Locked use and Operational Prohibitions

The source lays out the safeguards for Locked use, the broader safety guidance for Computer Use as a whole, and the specific targets the feature cannot handle.

- Evidence
- Safeguards for Locked use:
- “The authorization window is short-lived and scoped to the current unlock attempt.”
- “Automatic unlock is available only to Codex during active computer use turns.”
- “Codex covers every display while the desktop is temporarily unlocked.”
- “If Codex detects local keyboard or pointer input, it relocks the Mac and pauses automatic unlock until you unlock it manually.”
- For Computer Use overall, Codex can “view screen content, take screenshots, and interact with windows, menus, keyboard input, and clipboard state in the target app”.
- Users are also told to treat “visible app content, browser pages, screenshots, and files opened in the target app” as context that Codex may process while carrying out the task.
- The following safety guidance is provided.
- “Give Codex one clear target app or flow at a time”
- “You can stop the task or take over your computer at any time”
- “Keep sensitive apps closed unless they’re required for the task”
- “Avoid tasks that require secrets unless you’re present and can approve each step”
- “Review app permission prompts before allowing Codex to use an app”
- “Use Always allow only for apps you trust Codex to use automatically in future tasks”
- “Stay present for account, security, privacy, network, payment, or credential-related settings”
- “Cancel the task if Codex starts interacting with the wrong window”
- When using a browser, “it can interact with pages where you’re already signed in”.
- It warns that websites may contain “malicious or misleading content”.
- If you want to use things in parallel, the guidance is to “ask Codex to use a different browser”.
- As a functional limitation, it “can’t automate terminal apps or Codex itself”.
- The reason given is “since automating them could bypass Codex security policies”.
- It also “can’t authenticate as an administrator or approve security and privacy permission prompts on your computer”.
- For changes made through a GUI, they “may not appear in the review pane until they’re saved to disk and tracked by the project”.
- On data handling, “Your ChatGPT data controls apply to content processed through Codex, including screenshots taken by computer use”.
- Implications
- The protections in Locked use are consistently designed to conceal and minimize the unlocked state itself while preventing simultaneous local use.
- Because browser content, clipboard state, screen contents, and screenshots all fall within scope, the working area needs to be kept tight in any environment containing sensitive information or signed-in sessions.
- The fact that terminal apps and Codex itself are excluded from automation targets can be read as a design constraint intended to prevent Computer Use from bypassing Codex’s existing security policies.
- Because it cannot perform administrator authentication or approve security/privacy permission prompts on the OS’s behalf, high-privilege OS operations still require human involvement.
