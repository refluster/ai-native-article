## Executive Summary

Databricks は 2026 年 7 月 8 日、自社エンジニアが実際に処理したコーディングタスクでモデルとハーネスを評価した社内ベンチマークの結果を公開した。オープンモデルの GLM 5.2 が品質で Opus 4.8 と統計的に同点でありながらタスク単価は $1.28 対 $1.94 と安く、トークン単価はタスクの実コストの指標として不十分だと結論づけた。さらに同一モデルでもハーネスの違いだけでタスク単価が2倍以上動くことを示し、モデル選定だけでは効率化は完結しないとした。

分析全体からの主要な結論は4つに集約される。第一に、コーディングタスクのパレートフロンティア（あるコストで得られる最良の品質）には OpenAI、Anthropic、そしてオープンソースのモデルがすべて含まれる。すなわち今日、フロンティア性能を提供できるのは複数ツールの組み合わせだけである。第二に、オープンモデル、とりわけ GLM 5.2 は最高難度のタスクさえこなせるようになった。第三に、モデルのトークン単価はエンドツーエンドのタスクで生じる実コストの指標として不十分で、より大きなモデルの方がトークン効率で優り総コストが低くなり得る。第四に、モデルを呼び出すハーネスがコストと品質を大きく左右し、多くの場合 Pi のような単純なハーネスが最も良い結果を出した。

## なぜ公開ベンチではなく自社の PR からベンチを作ったのか

Databricks は SWE-Bench や TerminalBench といった公開ベンチマークの限界を2点挙げる。第一に、タスクが公開されているため解答が時間とともに学習データに漏れ込む。第二に、Scala・Go・Rust・Java・Python・Bazel・Protobuf など10以上の言語にまたがる自社コードベースにとって、結果が代表的でなかった。

そこで同社は自社のマージ済みプルリクエストからベンチを構築した。エンジニアは1日に数千件のコード変更をマージしており、コミット履歴・人間によるレビュー・テストを備えた PR は良質な素材になる。ここに次の品質フィルタを適用した。

- **Recency（新しさ）**：現在使っているフレームワークや規約を反映するよう直近の履歴から抽出
- **Human written（人手による記述）**：ボットコミット、サービスアカウント、完全な AI 生成・自動生成の変更を除外
- **高品質なテストスイートを伴う**：変更を検証できるテストを含む PR に限定
- **Self-contained（自己完結）**：変更が少数のモジュールに閉じている
- **典型タスクの代表性**：Scala バックエンド、Rust システムコード、React/TypeScript フロントエンド、protobuf/gRPC、Bazel 設定などフルスタックにわたる分布から選定
タスク化では PR の意図をくみ取ってプロンプト化し、解決策の説明を削って問題・ゴール・制約だけを残した。テストファイルは切り出して held-out とし、非テストファイルの変更をモデルが自力で再現する形にした。各サンプルは手作業で評価し、必要に応じてテストを（AI を使わず）書き直した。正誤判定に LLM ジャッジは用いていない。「正しくあることより正しく聞こえることを報奨してしまう」ためだという。

## 3つの能力ティアと「タスクをルーティングする」設計

結果はモデルとハーネスが明確に3つの能力ティアに分かれた。最上位の最も賢いモデルはあらゆる問題に有効だが非常に高価で、中位・下位のモデルも一般的なタスクでは高い有効性を保ちつつ大幅に安い。

Databricks 社内では従来、既定モデルが常に最も高価なものだった。今回の分析を受け、フラグの切り替えや設定更新のような一般的な運用タスクは、より安価な Haiku や GPT 5.4 Mini クラスに寄せるべきだと判断した。ログ分析でも、タスクの約4分の1が低複雑度、約60%が中複雑度とタグ付けされており、効率改善の余地は大きかった。

## トークン単価ではなくタスク単価で見る

トークン単価はタスク全体のコストを予測できない、というのが中核の発見である。推論効率がモデル間で大きく異なるためだ。

- **GLM 5.2**：最上位ティアに入り、品質で Opus 4.8 と統計的に同点。それでいてタスク単価は $1.28 対 Opus の $1.94。
- **Sonnet 5 対 Opus 4.8**：Sonnet 5 はトークン単価で Opus より約1.7倍安い。しかし実タスクでは Sonnet が $2.09/タスク対 Opus の $1.94 と逆に高くつき、タスク完了率も6ポイント低かった（81% 対 87%）。Sonnet 5 がより長く動きより多く読み、1.9倍のトークンを消費したためである。
つまりオープンモデルはコーディングでも「デイリードライバー」になり得る段階に達しており、より大きなモデルがトークン効率で上回って総コストを下げる場合がある。

## ハーネスがコスト効率を大きく左右する

同一モデルを同一の thinking effort で、Claude Code/Codex と Pi という2つのハーネス経由で走らせたところ、品質は同等のままタスク単価が場合により2倍以上異なった。差の主因は各ターンでモデルに渡すコンテキスト量だった。Pi は1ターンあたり約3分の1のコンテキストしか送らず、作業セットを絞って少ない実行回数でタスクを終えた。

このため Databricks の結論は「あるハーネスが常に安い」でも「ネイティブハーネスが劣る」でもなく、モデル選択はパズルの一片にすぎない、というものだ。同社はモデルとハーネスの入れ替えをシームレスにするため Omnigent に投資している。

## ベンチを歪めた抜け穴：Git 履歴を封じる

初期の実験では、いくつかのモデルのスコアが「出来すぎ」に見えた。トレースを手作業で調べたところ、当初のセットアップでは「正解」の実装がワークツリーの Git 履歴からまだ復元可能だったことが分かった。各タスクはマージ済みコミットに由来するため、シェルを持つエージェントが Git 履歴を辿って正解に到達するのを止めるものが何もなかったのである。これを修正するため、Databricks は実行のあいだ作業コピーをリポジトリから完全に切り離し、Git 履歴を封印した。

この一件は、自社データでベンチを作る際の落とし穴を示すと同時に、その手法が再現可能であることも示す。マージ済み PR のバックログを持つチームは、どのモデルも学習しておらず、自チームの書いたテストで採点されるベンチマークを既に抱えている——それが同社の主張である。Databricks はより難しいタスクを継続的に追加し、新しいエージェントやハーネスをすべてこのベンチに通していくとしている。
