## Executive Summary

Yiqi Wang らのサーベイ論文「From Agent Traces to Trust: A Survey of Evidence Tracing and Execution Provenance in LLM Agents」(arXiv:2606.04990v4) は、自律的に動くLLMエージェントの信頼性を「最終回答の正しさ」ではなく「実行過程そのものの追跡可能性」で捉え直すことを主張する。論文はこの過程が抜け落ちた状態を **process-level accountability gap（過程レベルの説明責任の穴）** と名付け、エージェント実行を6次元の分類体系で整理する枠組みを提示する。焦点は、どの証拠がどの主張を支えたかを検証・デバッグ・安全制御・監査へつなぐ「来歴（provenance）」の設計にある。

## なぜ「正解したか」だけでは足りないのか

論文の出発点は明快だ。「Final-answer accuracy evaluates only the endpoint of an execution; it does not explain how an output was produced, which evidence supported each claim（最終回答の精度は実行の終点だけを評価し、出力がどう生成されたか、どの証拠が各主張を支えたかを説明しない）」。ツール呼び出し、検索、メモリ、マルチエージェント通信を横断して動くエージェントでは、答えが合っていても、その答えが正当な根拠から導かれたのか、汚染された入力の産物なのかを事後に区別できない。

論文はここで二つの概念を明確に分離する。

- **実行来歴（execution provenance）**: エージェント実行全体を型付きグラフで表現したもの。証拠ユニット、実行成果物（検索文書・ツール呼び出し・メモリアクセス・主張・アクション）と、それらの因果・依存・矛盾の関係を含む「完全な」表現。
- **証拠追跡（evidence tracing）**: 来歴のうち、証拠とエージェントの主張・判断・アクションを結ぶ「支持関係」だけに射影した部分問題。
**含意**: 「証拠追跡」は「実行来歴」の一部にすぎない。多くの既存研究がRAGの引用付与など証拠追跡に集中する一方で、ツールやメモリをまたぐ完全な来歴グラフはまだ手つかず、という論文の問題設定がここから導かれる。

## 6次元の分類体系:何を、どの粒度で、いつ記録するか

論文の中核はTable 1「Taxonomy of evidence tracing and execution provenance in LLM agents」に集約される6次元の分類だ。設計の選択肢を次のように整理する。

- **トレース源（Trace sources）**: 推論、検索、ツール利用、MCP境界、メモリ、環境、マルチエージェント通信
- **証拠・実行ユニット**: 文書、パッセージ、観測、ツール出力、メモリ項目、主張、ポリシー、アクション
- **来歴関係（Provenance relations）**: support, derive, depend-on, contradict, invalidate, trigger, update, use, generate
- **粒度（Granularity）**: 実行全体（run-level）からトークン・スパン単位まで
- **タイミング**: 事前実行、実行時、事後、連続
- **表現形式**: 構造化ログ、実行グラフ、証拠グラフ、主張支持グラフ、実行時状態
表現形式については、Figure 3「Running example of a provenance graph」で、クエリ・パッセージ・主張・ツール・メモリ・アクションの間に Support / Derive / Depend-on / Contradict / Invalidate / Update といった型付き関係を張った具体例を示す。**評価と結論の分離**: 論文の主張は、フラットな時系列ログではなく、この型付きグラフとして表現して初めて「どの証拠がどの主張を支え、どこで矛盾が生じたか」を機械的に追えるようになる、という点にある。

## ツールとメモリ — 来歴が守る二つの攻撃面

論文が来歴の実用的価値を最も具体的に示すのが、ツール利用（Section 4）とメモリ（Section 5）だ。

ツール利用では、**間接プロンプトインジェクション** が中心的脅威として挙げられる。外部コンテンツがツールのコンテキストを汚染しうるため、情報フロー追跡とテイント（汚染）追跡が要る、という診断だ。代表的な防御手法として次を挙げる。

- **Agent-Sentry** — 引数ごとのデータフロー追跡
- **FIDES** — 情報フローラベル
- **NeuroTaint** — 意味的変換をまたいだテイント伝播
メモリについては、論文はメモリを「provenance-bearing evidence（来歴を担う証拠）」として扱い、書き込み系譜・検索妥当性・矛盾管理・検証の4側面で捉える。そのうえで Table 4「Agent memory through a provenance lens」が11システムを write / retrieval / conflict / staleness / verification の観点で採点する。論文の評価は辛辣だ。**MemGPT、A-MEM、Mem0 といった現行メモリシステムは「recall over accountability（説明責任より想起）」を重視しており、矛盾処理と汚染追跡が手薄** だと指摘する。

**含意**: ツールもメモリも、権限や想起性能だけを設計してきた。来歴（引数レベルの系譜、書き込み元の帰属）を対にして初めて、攻撃と正当な入力を区別できる、というのが論文の一貫した論旨だ。

## ベンチマークの断片化と6つの未解決課題

論文は Figure 5「Benchmark coverage heatmap」で、7つのベンチマーク系統を7つの評価能力にわたって Strong / Partial / Limited で採点する。強い領域はRAG/帰属（証拠）、ツール利用、セキュリティ攻撃。弱い領域はコンポーネント横断の連鎖、関係アノテーション、リカバリ志向の評価だ。

指摘される決定的な欠落は明快である — 証拠ラベル・ツール呼び出し・メモリ・マルチエージェント通信・安全性・来歴関係・リカバリを **エンドツーエンドで一体カバーするベンチマークが存在しない**。

Section 7 が挙げる未解決課題は6つ。

1. **統一トレーススキーマ** — システム間で形式が非互換で比較を妨げる 2. **意味・主張レベルの来歴** — 細粒度の支持関係が依然困難 3. **メモリとマルチエージェントの来歴** — セッション横断・エージェント横断の責任所在が不明 4. **実行時の安全性と強制** — オンラインでのポリシー準拠来歴が未開拓 5. **現実的なベンチマーク** — 既存データセットに実行トレースが欠ける 6. **プライバシーに配慮した監査基盤** — 来歴収集自体がデータ露出リスクを生む

この6課題は、冒頭の「過程レベルの説明責任の穴」を各コンポーネントに割り付けた作業リストに等しい。論文の貢献は、完全な実行来歴グラフと証拠支持の射影を区別し、6次元分類でトレース設計空間を整理し、ベンチマークを来歴能力へ対応づけて、横断評価・関係アノテーション・リカバリ機構の空白を名指ししたことにある。継続更新のためのリポジトリ（github.com/xiaoqi-7/Agent-Tracing-Survey）も公開されている。
