## Executive Summary

LlamaIndex 共同創業者の Jerry Liu は、2026年7月15日に公開した X の長文記事「The Best Model Routing is Task Specific」で、モデルルーティングの最適解は汎用の一枚岩ではなく「タスク特化」にあると論じた。直近約1.5か月に登場した OpenRouter の「Fusion」と Cognition の「Devin Fusion」は、いずれも単一のフロンティアモデルに依存せず、複数モデルをタスクに応じて束ねる／切り替える設計を採る点で、その主張を具体化している。本稿は、この二つの実装が「タスク特化ルーティング」をどう体現しているかを、公表された仕様とベンチマーク数値に沿って整理する。

## 「モデルルーティング」がなぜ今の争点なのか

Jerry Liu の記事は「Model routing is so hot right now.（モデルルーティングは今まさに熱い）」という一文から始まる。単一の最強モデルを常用するのではなく、入力やタスクに応じて複数モデルを使い分ける発想が、直近1.5か月で相次いで製品化されたことが背景にある。

論点は「どのモデルを選ぶか」から「どう束ねるか・いつ切り替えるか」へ移りつつある。記事のタイトルが示す主張は明快で、最良のルーティングは万能の汎用戦略ではなく、解こうとしているタスクに特化した設計だ、という点にある。Jerry Liu はその根拠として、対照的な二つの実装を挙げる。プロンプトを複数モデルのパネルに扇状に配って一つの回答へ合成する OpenRouter の Fusion と、コーディングという特定領域に最適化した Cognition の設計である。

- 記事は X の長文記事フォーマットで公開され、投稿は43.4Kビューを記録している(2026年7月15日時点)。
- 提示される二つの実装は、いずれも「複数モデル」を前提に置く一方、束ね方の思想が正反対に近い。
## OpenRouter Fusion:フロンティアモデルのパネルを「合成」する

OpenRouter が公開した Fusion は、一つのプロンプトを複数のフロンティアモデルからなるパネルへ並列に投げ、各モデルの独立した回答を収集したうえで、専用の「ジャッジ(judge)」モデルがそれらを一つの構造化された最終回答へ合成する複合(compound)モデルである。Jerry Liu が記事で「compound model that fans your prompt out to a panel of frontier models and synthesizes one answer」と要約した通りの構造だ。

公表されている仕様とベンチマークは以下の通り。

- Fusion は2026年3月31日に公開実験として登場し、6月中旬に OpenRouter API の本番統合に至った。
- モデルのスラッグは `<task>-<tier>` の形式を採る。`task` はパネルを最適化する対象タスク、`tier` は品質・コスト・速度のトレードオフを指す(`high` は最強モデル群、`budget` は同じフロンティア級ジャッジを保ちつつ安価なパネル、`fast` は各モデルの初回トークン到達時間が揃った低遅延パネル)。
- ベンチマークでは、Fable 5 と GPT-5.5 を融合したパネルが69.0%を記録し、単体の Fable 5(65.3%)を含むすべての個別モデルを上回った。
- 低コスト構成(Gemini 3 Flash、Kimi K2.6、DeepSeek V4 Pro)は GPT-5.5 と Opus 4.8 を上回り、Fable 5 単体のスコアに1%以内まで迫りながらコストは半分だった。
- 既定の「Quality」プリセットは、パネルに Claude Fable 5 と GPT-5.5 を据え、合成役のジャッジに Claude Opus 4.8 を用いる。
ここから読み取れるのは、Fusion がスラッグの命名規則そのものに「タスク」を第一級の軸として組み込んでいる点だ。パネルの構成と階層は、汎用の一設定ではなく、最適化したいタスクごとに選ぶ前提で設計されている。

## Cognition Devin Fusion:セッションの途中で「切り替える」

もう一方の実装が、Cognition が6月29日に公開した Devin Fusion である。こちらは高価な「メインエージェント(main agent)」一つと安価な「サイドキック(sidekick)」一つを組み合わせるコーディング用ハーネスで、フロンティア級の出力をコスト35%減で実現すると主張する。

Fusion がプロンプト単位で並列合成するのに対し、Devin Fusion のルーティングは連続的で、セッションの途中で行われる。

- エンジニアリングのタスクは難度が終盤で判明することが多い。Cognition が挙げる例は「単純なバグ」に見えたものが複数ファイルにまたがる競合状態(race condition)だったというケースで、複雑性が露呈した時点で作業をフロンティアモデルへ戻せる。上流での見積もりに固定されない。
- モデルの切り替えは「コンパクション(会話要約)」の境界に合わせて行われる。通常、モデルを入れ替えると高価なキャッシュが失われるが、会話がちょうど要約されるタイミングではキャッシュミスがいずれにせよ避けられない。そのため、切り替えのコストは実質的に無料になる。
Devin Fusion が体現するのは、コーディングという領域固有の性質(難度が事後的に判明する、キャッシュ境界が存在する)に合わせてルーティングを設計するという発想である。汎用のルーターでは、この「途中で戻す」「要約境界で切り替える」といった最適化は生まれにくい。

## 「タスク特化」が意味するもの

二つの実装は、束ね方こそ「並列合成」と「逐次切り替え」で対照的だが、結論は一致する。単一モデルへの依存を外し、タスクの構造に合わせてルーティングを設計するという方向だ。

- OpenRouter Fusion は、`<task>-<tier>` というスラッグ設計を通じて、タスクを選択軸としてルーティングに埋め込む。
- Cognition Devin Fusion は、コーディング特有の難度判明タイミングとキャッシュ境界を利用し、セッション内でモデルを動的に切り替える。
Jerry Liu の主張「The Best Model Routing is Task Specific」は、この二例を並べると具体的な設計原則として立ち上がる。汎用の「常に最強モデル」でも、汎用の「常に安価モデル」でもなく、タスクの性質——並列の視点が効くのか、難度が後から判明するのか——に応じてルーティングを組む。それが、直近1.5か月に市場が出した回答である。
