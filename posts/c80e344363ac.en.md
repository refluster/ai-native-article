## Executive Summary

An OpenAI Developers blog post (September 11, 2026, bylined Eric Provencher) argues that the instruction layer for coding agents — skill descriptions, AGENTS.md, and task prompts — has kept accumulating in the style earlier models required, and that this bloat now actively hurts GPT-6 Astra rather than helping it. Drawing on concrete before/after examples from a recent update to the skill-creator skill, the post's core claim is simple: as models get more capable, their surrounding instructions need to get shorter and more specifically scoped, not longer.

## Skill Descriptions Exist to Narrow "When," Not to Explain "What"

The post is blunt about where the common practice of stuffing many skills into a project leads. "Each skill comes with a name and description that are loaded into the model's context so it knows when to use them" — but when descriptions run too long, adding more skills causes Codex itself to start truncating them, so the model sees less of each one. Worse, "descriptions can often contradict each other or over-emphasize when skills should be used, leading the model to load instructions that don't actually help the task."

The post quotes the exact contrast used in the skill-creator update:

- **Bad**: "Create and validate Postgres schema migrations. Use when working with databases, queries, models, or persistence."
- **Good**: "Create and validate Postgres schema migrations. Use when adding or changing a migration, or reviewing its rollout."
The bad version invites the model to load the skill "any time anything touches a database"; the good version scopes it to "adding, changing, or reviewing a migration's rollout." That single line is the difference between the skill firing for irrelevant tasks and firing only when it should.

The second principle is progressive disclosure. Reading a skill's body itself consumes context and pushes the session closer to compaction. Skills with multiple workflows should keep their root document as a minimal router, pointing to supporting docs and scripts rather than forcing the model to read everything up front. The post adds that repository skills are also read by other contributors' agents, running different models — "guidance that helps Sol or Luna may overconstrain GPT-6 Astra" — so authors need to consider which models will actually consume the instructions they leave behind.

## AGENTS.md Should Be an Index You Consult, Not a Book You're Made to Read

Because AGENTS.md applies to every edit in a repository, the post argues each instruction inside it deserves frequent re-examination. It offers a parallel bad/good pair:

- **Bad**: "Before every edit, read architecture.md, database.md, and deployment.md."
- **Good**: "Use architecture.md for service boundaries, database.md for schema changes, and deployment.md when preparing a deployment."
Requiring a full document review before fixing a typo is excessive; GPT-6 Astra, the post says, "can work out what it needs to read without being pushed to review the whole project before every change." Pointers to documentation remain useful — but only when they're contextual to the task at hand, not blanket requirements.

The same shift applies to testing. Earlier models needed explicit encouragement to run tests and check their work; GPT-6 Astra does this on its own, so identical encouragement can now trigger unnecessary testing. The post's suggested rewrite defines the safe boundary instead of pushing the behavior: "The local tests use disposable fixtures and have no production access. Run them, fix failures caused by the requested change, and rerun affected tests without asking for approval at each step." The instruction shifts from *prompting the action* to *defining how far it may go unsupervised*.

## Decision Boundaries: An Operating Knob That Needs Re-Tuning Per Model, Not a One-Time Fix

The post's sharpest, most concrete section is on decision boundaries. "If a previous model did things on your behalf without permission, you may have added strong language to make it ask first" — many teams have accumulated exactly this kind of defensive phrasing from past experience. But GPT-6 Astra is described as "our most aligned model," one that "will not perform tasks unless it knows it is safe." The same strong gating language that once protected against overreach can now stop the model from continuing work it should be allowed to finish.

Crucially, the post frames this not as a bug to patch once but as an operating parameter to revisit with every model generation: "consider updating that language: Astra could take it too seriously and may stop work where you'd actually be happy for it to continue." The instruction is to re-calibrate the strength of the boundary language against the model's actual demonstrated judgment, not to leave old guardrail text standing indefinitely.

## Define "Done" Up Front, or Astra Will Stop Too Early

The persistence section follows the same shape. GPT-6 Astra is described as more tentative than the prior GPT-5.6 Sol about continuing for long stretches: "it may reach a first implementation and come back for your review while there's still work to do." The fix isn't a pep talk — it's defining completion criteria before the task starts. Getting the implementation running, inspecting the result, and fixing what fails should be stated as part of the request; otherwise, "a requirement to stop for review after the first implementation will pull the model toward an earlier stopping point." A routine review checkpoint, left unstated as optional, quietly drags the model toward stopping sooner than intended.

The post closes by suggesting the review process itself can be delegated back to the model: "ask GPT-6 Astra to do an audit based on what was discussed in this article." Maintaining the instruction layer, in other words, has itself become a task the model can be handed.

## What the Post Adds Up To

Across all four sections, the common thread isn't a single technical fix but an operating discipline: as model capability rises, the instructions surrounding it must be actively trimmed and re-tuned, not left to accumulate. Skill descriptions, AGENTS.md, decision boundaries, and completion criteria are each treated as adjustable parameters that need re-examination at every model transition, not settled text. The practical implication for teams running agents is direct — defensive language stacked up for an older, less reliable model can become noise, or worse, a performance drag, on the next one.
