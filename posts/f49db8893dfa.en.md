## ECC: What’s Implemented in the “Agent Harness Performance Optimization System” for Claude Code/Codex/Cursor

## Executive Summary

ECC is a GitHub repository designed not as a simple configuration bundle, but as “The harness-native operator system for agentic work,” integrating “skills, instincts, memory optimization, continuous learning, security scanning, and research-first development” into a single system. In the source materials, it is positioned as an operational foundation that can be reused not only with Claude Code, but also across multiple harnesses such as Codex, Cursor, OpenCode, Gemini, Zed, and GitHub Copilot.

On the public-facing side, it offers “60 agents, 232 skills, and 75 legacy command shims,” and `ECC v2.0.0-rc.1` adds a GUI dashboard, a Rust-built control-plane prototype, expanded operator workflows, and a status feature for portable handoff. The implication is that ECC is not about distributing prompts or one-off commands, but about open-sourcing a “harness operations layer” that unifies execution, state management, continuous learning, and auditing for AI coding environments.

## How ECC Positions Itself: Not a Config Bundle, but an “Agent Harness Performance System”

In short, ECC is presented not as a collection of config files for AI agents, but as a production-oriented system that runs across multiple development harnesses.

- Evidence

- In the README, it is defined as “The harness-native operator system for agentic work. From an Anthropic hackathon winner.”
- It further states: “Not just configs. A complete system: skills, instincts, memory optimization, continuous learning, security scanning, and research-first development.”
- As supported targets, it lists “Claude Code , Codex , Cursor , OpenCode , Gemini , Zed , GitHub Copilot , and other AI agent harnesses”
- It also highlights its public scale with “170+ contributors,” “12+ language ecosystems,” and “182K+ stars | 28K+ forks”
- Conclusion
- ECC’s core claim is not prompt optimization or a standalone IDE plugin, but the standardization of an “operations layer” that sits above the AI agent execution environment
- Phrases such as “harness-first release” and “cross-harness parity” indicate that reproducibility and behavioral consistency across harnesses—not any single model or IDE—sit at the center of the design
- The repository structure also spans `agents/`, `skills/`, `hooks/`, `rules/`, `mcp-configs/`, `schemas/`, `research/`, and `tests/`, covering a much broader scope than simple template distribution

## Installation and Operational Policy: Do Not Mix the Plugin Path and the Manual Path

In the README, a substantial amount of explanation is devoted less to setup steps themselves than to avoiding fragile installation patterns.

- Evidence
- At the start of Quick Start, it explicitly says: “Pick one path only”
- “Do not stack install methods. The most common broken setup is: `/plugin install` first, then `install.sh --profile full` or `npx ecc-install --profile full` afterward.”
- As the recommended path, it shows:
- `/plugin marketplace add https://github.com/affaan-m/ECC`
- `/plugin install ecc@ecc`
- To clarify identifier differences, it lists:
- “GitHub source repo: `affaan-m/ECC`”
- “Claude marketplace/plugin identifier: `ecc@ecc`”
- “npm package: `ecc-universal`”
and states that “they are not interchangeable”

- Regarding rule distribution limits after plugin installation, it notes: “Claude Code plugins cannot distribute rules automatically.”
- Accordingly, it provides steps to manually copy `rules/common` and `rules/typescript` into `~/.claude/rules/ecc/`
- Manual install is described as: “Use this only if you are intentionally skipping the plugin path: `./install.sh --profile full`” and “If you choose this path, stop there. Do not also run `/plugin install` .”
- For uninstall and recovery, it points users to `node scripts/uninstall.js --dry-run`, `node scripts/uninstall.js`, `node scripts/ecc.js doctor`, and `node scripts/ecc.js repair`
- Conclusion
- While ECC is feature-rich, overlapping installation paths directly lead to duplicated behavior, duplicated skills, and duplicated hooks, making installation policy itself part of the product specification
- The strict separation between `plugin` and `manual` is not just a UX choice, but an operational control meant to avoid runtime conflicts
- Since rules cannot be distributed automatically through the plugin path, ECC decomposes distribution into `plugin`, `manual copy`, and `CLI installer`, explicitly working within the limits of harness functionality

- The combination of `SQLite state store`, `query CLI`, `session adapters`, and `status snapshots` indicates a design centered not on conversation logs, but on structured state
- The presence of `ECC_HOOK_PROFILE` and `ECC_DISABLED_HOOKS` suggests that although ECC assumes strong automation, it still leaves room to reduce load and intervention for low-context environments or local-model setups
## ECC’s Cross-Harness Implementation Strategy: Rewriting Hooks in Node.js and Detecting Package Managers

To support multiple IDEs and CLIs, ECC explicitly lays out the foundational work it has done to secure compatibility.

- Evidence
- The README states: “This plugin now fully supports Windows, macOS, and Linux , alongside tight integration across major IDEs (Cursor, Zed, OpenCode, Antigravity) and CLI harnesses.”
- It continues: “All hooks and scripts have been rewritten in Node.js for maximum compatibility.”
- As its package manager detection priority, it lists:
- `CLAUDE_PACKAGE_MANAGER`
- `.claude/package-manager.json`
- `package.json : packageManager field`
- lock file
- `~/.claude/package-manager.json`
- fallback
- As setup commands, it provides:
- `node scripts/setup-package-manager.js --global pnpm`
- `node scripts/setup-package-manager.js --project bun`
- `node scripts/setup-package-manager.js --detect`
- In `v1.7.0`, it added: “Codex app + CLI support”
- In `v1.6.0`, it introduced: “Codex CLI support — New `/codex-setup` command generates `codex.md` for OpenAI Codex CLI compatibility”
- In `v1.3.0`, it added: “Full OpenCode integration”
- In `v1.8.0`, it notes: “Cross-harness parity — behavior tightened across Claude Code, Cursor, OpenCode, and Codex app/CLI.”
- Conclusion
- ECC’s cross-harness strategy is not an abstract claim that it “runs anywhere,” but a concrete approach that aligns hook implementations, package management, installers, documentation, and compatibility commands one by one
- “All hooks and scripts have been rewritten in Node.js” should be read as a compatibility measure meant to reduce OS-level differences and shell dependencies
- As a result, ECC behaves not as an extension for Claude Code alone, but as a packaging system that can carry the same catalog across multiple harnesses
