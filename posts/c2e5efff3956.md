# エージェント時代に「頭」を失うソフトウェア：UI優位からデータ・権限・実行層への防御力シフト

## Executive Summary

Seema Amble は、エージェント化によって従来の SaaS の防御力が UI から剥がれ、より下位の「data models, permissions, workflow logic, and compliance」と、より上位の「networks, proprietary data generation, and real-world execution」に移ると論じる。起点となるのは、2026年5月13日の記事が取り上げる Salesforce の「headless product」発表であり、そこから「UI を剥いで database を exposed したとき、何が残るのか」という問いが立てられている。

記事の中心命題は明確である。エージェントは「muscle memory as a moat」を弱めるが、「operational logic and context as a moat」は消さない。むしろ、エージェントが安全に行動するには明示的なルール、権限、プロセス定義が必要になるため、その重要性は増す。

## Salesforce の「headless product」が示した論点：UI を外した後に何が残るのか

Salesforce の発表は、新技術そのものよりも、システム・オブ・レコードの価値の置き場所を再定義するシグナルとして扱われている。

- エビデンス
- 記事は「Last month Salesforce announced it would open its APIs and launch a headless product」と述べる。
- その狙いは、「in an agentic world, its value lies in the data layer, not the UI」という再ポジショニングだと整理されている。
- 同時に筆者は、「not much appears to have changed technically: the APIs Salesforce is now marketing as a “headless product” have largely existed for years」と留保を付す。
- headless の発想は、「agents can access the data from the system of record without needing to interact with the UI」にある。
- 結論
- 論点は API 公開の新規性ではなく、SaaS の価値が「人間が使う画面」から「機械が読むデータ層」へ移るという前提にある。
- その結果、従来の SoR の防御力を支えていた UI 起点の優位は再評価を迫られる。
- 記事の問いは、「How is that different from a Postgres database, a well-designed schema, and an API?」であり、headless 化は SoR を“ただのデータベース”と区別していた要素の棚卸しを要求する。
## 「The UI was the product」だった時代の粘着性スコアカード

記事はまず、SoR がなぜ長く乗り換え困難だったかを、人間中心の運用実態に分解している。

- エビデンス
- SoR は「the authoritative source of truth for a given domain of business data」と定義される。
- 具体例として、「A CRM is the system of record for revenue. An HRIS is the system of record for people. An ERP is the system of record for money」と記されている。
- Salesforce については、「The dashboards, pipeline views, forecasting tools, and activity feeds were what people were buying」とされる。
- UI の役割として、記事は以下を列挙する。
- 「The UI drove stickiness」
- 「It enforced data hygiene」
- 「It created shared vocabulary: Leads, Opportunities, Accounts」
- 「It made thousands of sales reps enter data they otherwise wouldn’t have」
- さらに Salesforce の持続性は、「many sales leaders insist on bringing Salesforce with them to new jobs not because the UI is good, but because it is muscle-memory」と説明される。
- 歴史的な評価軸として、記事は次を挙げる。
- 「How frequently is it accessed?」
- 「Is it write-only or read-write?」
- 「How many undocumented SOPs are there?」
- 「Are there a lot of internal or external dependencies?」
- 「How critical is the data from a compliance perspective?」
- 比較対象として、「Replacing your ATS is painful but survivable. Replacing your CRM is open-heart surgery. Replacing your ERP is open-heart surgery while the patient is running a marathon」と記される。
- 結論
- 従来の SoR の粘着性は、データ保存そのものより、人間が日々 UI 上で行う入力・閲覧・承認・会話の習慣に強く依存していた。
- 特に CRM の強さは、読み書きが双方向で継続し、管理 cadence や SOP が画面と一体化していた点にある。
- ERP が最も動かしにくいのは、運用依存だけでなく、監査人・規制当局まで含む外部接続と法的真正性を抱えるためである。
- 一方で記事は、従来の SoR は「proprietary data」や「network effects」をほとんど moat 化できていなかったとも指摘する。過去の防御力の中心は、あくまで workflow と UI だった。
## エージェントは何を消し、何を残すのか：muscle memory の終わりと operational logic の残存

記事の転換点は、エージェントがブラウザ UI を前提としないことにある。

- エビデンス
- 記事は「An agent doesn’t need a browser. It needs an API, context, instructions, and the ability to act」と定義する。
- その背景として、
- 「LLMs became capable enough to reason」
- 「MCP standardized tool access」
が挙げられる。

- その結果、「An agent with MCP access to your platform can do what a human user does in milliseconds, at scale, without a browser」とされる。
- さらに、「With the right context, computer-using agents should be able to navigate incumbent software interfaces without even needing APIs」とまで述べる。
- 買い手の選択肢として記事は 3 つを明示する。
1. 「Incumbent system + agents」
1. 「DIY the system of record entirely」
1. 「Buy an AI-native replacement」
- 歴史的スコアカードのうち、消えるものとして「frequency of access」や「read vs. read-write」が挙げられ、「Agents may kill muscle memory as a moat」と総括される。
- 一方で残るものとして、
- 「Undocumented SOPs stay important in the short-term」
- 「Connectivity is still hard to unwind and extends further」
- 「Compliance-critical data remains important」
が明示される。

- とくに権限については、「which agents are authorized to do what, on whose behalf, with what auditability?」が「one of the hardest unsolved problems」とされる。
- 結論
- エージェントは UI への習熟や利用頻度を起点とする優位を削る。人間のトレーニング負荷や“慣れ”は、長期的には moat になりにくい。
- しかし、業務ロジック、例外処理、承認経路、権限制御、監査可能性は残る。むしろ、エージェントが自律的に行動するほど、これらが安全装置として前景化する。
- したがって SoR の防御力は「誰が毎日ログインするか」ではなく、「どの agent が何を、誰の代理で、どのポリシー下で、どの監査証跡付きで実行できるか」に移る。
## AI-native SoR の新しい防御力：再構築困難性、独自データ、action layer、現実世界の実行

記事は、AI-native な新規ソフトウェアがどこに防御力を築けるかを、旧来のスコアカードではなく新しい判定軸で提示している。

- エビデンス
- 第一の軸は「How hard is it to recreate the SoR?」である。
- 記事は「AI lowers the cost of recreating the first 80% of a system of record」と述べる。
- ただし「The remaining 20%, which are the exceptions, approvals, compliance requirements, and edge-case workflows, is still what separates a useful wedge from a true replacement」と続ける。
- 第二の軸は「Is there meaningful proprietary data?」である。
- 防御的なデータとは「not the data you import; it’s the data your product uniquely causes to exist」だとされる。
- 具体的には「observed behavior, response rates, timing patterns, process outcomes, benchmarks, exception patterns and agent performance traces」が挙げられる。
- そして「the data is the context now」と定式化される。
- 第三の軸は「Does it own the action layer?」である。
- ERP の例として、「approving spend, triggering payroll, reconciling invoices, sending notices」が示される。
- 「Products that close the loop are more defensible because they sit inside execution, not just observation」と記される。
- 第四の軸は「Is there a real-world execution element?」である。
- 例として「DoorDash」が挙げられる。
- 防御力の源泉は、「they dispatch people, move goods, or complete the service」にある。
- 第五の軸は「Are there network effects?」である。
- 対象となる複数当事者の例として、「buyers and sellers, employers and employees, companies and auditors, vendors and customers, payers and providers」が列挙される。
- ネットワーク効果の中身は、
- 「shared workflow coordination」
- 「benchmarking and intelligence」
- 「trust and standardization」
で説明される。

- さらに「How technically capable is the buyer?」も重要な軸とされる。
- DIY は理論上可能でも、実際には「build, maintain, and continuously improve their own database, workflow logic, agent stack, and governance layer remain low」とされる。
- 対象領域として「manufacturing, construction back-office, industrial and field-service workflows, or for areas like accounting」が挙がる。
- 結論
- AI-native SoR の差別化は、単にデータを保持することではなく、その製品が行動を引き起こし、その結果として新しいデータ exhaust を継続的に生成できるかにある。
- 「最初の 80%」は AI により模倣可能になるが、残る「20%」である例外・承認・法令対応・エッジケース処理が完全代替の境界線になる。
- ネットワークや現実世界の実行が絡むと、その製品は単なる記録システムではなく、調整インフラへと変わる。
- 買い手の技術力が低い、あるいは内部エンジニアリング資源が薄い市場では、DIY の総コストはライセンス削減ではなく、実装・保守・複雑性に転化する。
## agentic schema と permissioning の再設計：人間向け業務オブジェクトから、意図・委任・例外処理へ

記事は、防御力の議論をデータモデルと権限モデルの再設計にまで踏み込んでいる。

- エビデンス
- 「the ontology needs to be different」と明言される。
- 旧来ソフトウェアは「built for dashboards, reports, and humans, capturing workflow」であり、オブジェクトは「opportunities, tickets, candidates, etc.」だった。
- これに対して「Agentic schema needs to capture reasoning, actions, state tracking, exception handling, delegation, and coordination across systems」とされる。
- その結果、「The native object model might become tasks, intents, threads, policies, or outcomes instead」と提案される。
- 権限管理についても、「permissioning needs to be updated for managing agents, not just humans」とされる。
- 含まれる問いとして、
- 「who can do what」
- 「through which agent」
- 「under what policy」
- 「with what approvals」
- 「with what audit trail」
- 「with what rollback / exception handling」
が挙げられる。

- 結論
- headless 化は UI を消す話にとどまらず、SoR の中核オントロジーを人間の閲覧・報告中心から、エージェントの推論・実行・委任中心へ組み替える話である。
- 旧来の CRM/ERP/HRIS のオブジェクトモデルを API 化するだけでは不十分で、agentic な実行単位を表現できる schema が必要になる。
- 権限も人間のロール管理では足りず、agent-to-agent interaction を前提とした identity と governance の層が構造的役割を持つ。
