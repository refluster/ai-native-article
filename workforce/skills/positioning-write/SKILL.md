# positioning-write

A launch-shaped deliverable. The form matters because each section is what a post-launch retrospective needs to ask "did this work?"

## Instructions

Five sections, ordered:

1. **Positioning** — one sentence completing "For {audience} who {pain}, this is {category} that {differentiator}, unlike {alternative}." If any blank can't be filled, the launch isn't ready.
2. **Audience** — who reads / hears this. Be concrete: not "developers" but "Tokyo-based JS-leaning indie hackers who already use Claude Code." If the audience is "everyone who follows the site," say so explicitly and accept the dilution.
3. **Channel** — where this lands. Note site-prominence vs. SNS push vs. Notion changelog vs. all-three. Each channel has different fidelity.
4. **Success metric** — what a "this worked" looks like by next Tuesday. One metric. Numeric if possible. If the metric is "qualitative — the operator's gut", say so; that's still a metric.
5. **Retraction trigger** — what observable would force pulling or amending the launch. C-1 / W-1 are non-negotiable; the retraction trigger names the *next* tier of "we'd take this down."

Length: 300-700 words in Japanese.

## When NOT to use

- The artefact is the launch announcement *itself* (the customer-facing copy). That's `article-draft` voice. This skill produces the operator-facing plan that surrounds that copy.
- The launch is for a feature that hasn't shipped yet — write a `plan-write` doc instead; positioning waits for the feature to exist.
