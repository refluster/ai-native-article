### Status-transition criteria

Epic-010's `Status` flips from `Draft` to `Implemented` only when **all four** of the following hold (per [Epic-010 §Acceptance criteria](docs/epics/epic-010-project-trust-boundary.md#acceptance-criteria) and the tracker's Definition of Done):

1. **Legacy `wf/{type}` keys removed.** Bare Secrets Manager keys (`wf/anthropic`, `wf/github`, `wf/notion`, …) are deleted after the `WfLegacyCredentialReads` CloudWatch metric, filtered to `Reason=fallback_bare`, has stayed at zero for ≥ 1 week. (Story 2-B ships the metric with two dimensions, `Reason=fallback_default` and `Reason=fallback_bare`; only the latter signals a remaining bare-key reader. The `fallback_default` dimension is expected to be non-zero in steady state — every project that hasn't shadowed a credential reads from `_default` and ticks the metric.) Tracked as a Story 2 follow-up PR; gated on Story 6 readiness so the credential vault UI is the only write surface.
2. **Dual-write window closed.** ✅ **Met** (C2 cutover; reconciled 2026-06-05 by Epic-012 Story 3, [#216](https://github.com/refluster/ai-native-article/issues/216)). The legacy `AGENT#{slug}/RUN#{ulid}` and `AGENT#{slug}/DELIV#{ulid}` **dual-writes** from Story 1 are removed — the success path writes EXEC only. Originally enforced by the structural absence tests in `workforce/lambdas/agent-runner/dual-write-tests.ts` (ZERO `putItem(runRow)` / `putItem(delivRow)` on the success path; `writeExec` → `appendExecution`). **Corrected 2026-08-01 (PR #523 review, lens ren E4):** that file no longer exists — it was deleted with the whole Lambda runner in `99aca10` (PR #241, ADR-0005 phase 4a), so this criterion has read as "mechanically enforced" by a deleted test since 2026-06-05. The criterion stays **✅ Met**: enforcement is now structural-by-deletion (there is no runner to dual-write from; EXEC rows originate solely from the CCR engagement write per ADR-0005 §5). The failure-path RUN error trail (`failRun`/`skipRun`/`throwRun`) is gone with the same tree — the residual failure-path ledger gap is tracked as FU-031. The residual *enforcement* gap — nothing now asserts that a future success path won't reintroduce `RUN#`/`DELIV#` siblings — is tracked as FU-034; re-introducing a dual-write would mean rebuilding a runner (ADR-0005 §5), so the risk is low but is carried in the ledger rather than left to be re-derived.
3. **Front-end agent profile migrated to the `EXEC` row family.** ✅ **Met** (landed ahead of Story 6; reconciled 2026-06-05 by Epic-012 Story 3). The `/workforce/agents/:slug` page (`workforce/app/src/pages/AgentProfile.tsx`) reads its execution history exclusively from `PROJECT#{id}/EXEC#{ulid}` via `fetchAgentExecutions` (`GET /agents/{slug}/executions` → GSI1 `AGENT#{slug}`), not from the legacy `RUN`/`DELIV` rows. The legacy `fetchAgentDeliverables` SPA read path was removed; the `GET /agents/{slug}/deliverables` route remains as a documented legacy/historical read with no SPA caller.
4. **`article-health`-equivalent audit is clean.** A workforce-side audit (0 truncated executions, 0 malformed `EXEC` rows) runs green for ≥ 1 week post-cutover. The `wf-audit` Lambda (`workforce/lambdas/audit/`) is EXEC-only post-C2 and emits `WfAuditTruncatedExecs` / `WfAuditMalformedExecs`; the ≥1-week-clean observation is the remaining operational gate. **Corrected 2026-08-01 (PR #523 review, lenses farah F3 / ren E5):** this criterion previously demanded zeros from `WfAuditOrphanExecs` (retired by the C2 cutover) and `WfAuditCrossProjectLeaks` (retired 2026-07-03 with the membership concept) — metrics nobody publishes, making the gate unsatisfiable as written. Restated above in terms of the two signals that exist (`workforce/lambdas/audit/handler.ts:8-43`, `:240`, `:246`). **This is a scope reduction, not a metric rename** (PR #526 cycle-1, lens nadia N1): cross-project leakage is no longer a *detectable condition*, not merely an unpublished metric — `workforce/lambdas/audit/handler.ts:166-169` records that the member concept was removed on 2026-07-03, so every registered agent participates in every project and a missing MEMBER row stopped being a violation. A reader of criterion 4 should therefore **not** conclude that the audit still witnesses isolation: it does not. What asserts the trust boundary now is per-project credential resolution (`wf/projects/{id}/{type}`, Epic-010 Stories 2/6) — an access-path guarantee, enforced at read time, not a swept invariant. Whether an Epic named "project-as-trust-boundary" should close with **no** post-hoc isolation signal at all is an open product question: if the answer is no, that is a **fifth criterion**, not an edit to the fourth. Flagged for operator sign-off with the restatement. The gate additionally cannot be *observed* until FU-032 lands: both audit alarms are `TreatMissingData: notBreaching`, so a week of clean zeros is today indistinguishable from a week in which `wf-audit` never fired.

Criteria **2 and 3 are now met** (the RUN/EXEC cutover and the front-end migration, reconciled by Epic-012 Story 3). Epic-010 stays in `Draft` pending the two that remain: criterion **1** (legacy `wf/{type}` bare-key removal, gated on the Story 6 vault UI) and criterion **4** (the audit's ≥1-week-clean operational observation).
