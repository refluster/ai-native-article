COGNITIVE GUILD / FOUNDING STORY

三つの実戦から、AI組織へ。

量産商品の品質を知る。米国SaaSの開発組織を動かす。事業売却を通じて、組織に蓄積すべき資産を見る。別々に見えた三つの経験が、いま一つのAI組織の設計につながっています。

Koh Uehara · 創業ストーリー · 2026年9月4日

Cognitive Guildは、本稿で用いる運営中のAgent Workforceの仮称です。既存サイトのSoftware Talent Networkと同じ取り組みを指します。

00 / THE CONSTRAINT

必要だったのは、もう一人のコーダーではなかった。

いま私は、米国カリフォルニア拠点で、米国市場におけるSaaSやマーケットリサーチに取り組んでいます。周囲には大きなテクノロジー企業が集まっています。しかし、近くに技術があることと、自分たちのプロジェクトに実行能力があることは別の話です。

ソフトウェアを担う技術者は、私一人です。必要な仕事は実装だけではありません。要求を整理し、設計し、品質を確かめ、セキュリティを点検し、運用し、得られたデータを分析する。市場や制度も追い続けなければなりません。

AIによってコードを書く速度が上がっても、この仕事の連鎖が自動的につながるわけではありません。そこで考え始めたのが、個々の作業を補助するAIだけでなく、役割・権限・評価・学習を備えた実行組織を持つことでした。

人を増やせないとき、組織が持てる能力まで増やせないのだろうか。

この問いへの取り組みが、Cognitive Guildです。現実の仕事量と能力の不足が切実な動機となり、このリポジトリのソフトウェア開発と記事制作は、仕組みそのものを試し、改善する場になっています。

01 / THREE FOUNDATIONS

AIの使い方より先に、組織の作り方を学んでいた。

AI組織の設計に持ち込んだのは、フレームワークの知識だけではありません。品質の厳しさ、人と仕事を動かす難しさ、そして組織や事業が蓄積すべき資産。その三つを、実務の異なる立場から経験してきました。

02 / PRODUCT DISCIPLINE

「動いた」の先に、商品を届ける仕事がある。

最初の土台は、コンシューマ機のソフトウェア開発です。1商品に数千人が関わる環境で、当社の商品開発プロセスを経験しました。QCDは資料の中の指標ではなく、開発、デバッグ、品質確認、量産立ち上げを通じて向き合う制約でした。

発売日に向けて揃うのは、ソフトウェアだけではありません。ハードウェア、工場、マーケティングのCM、流通の手配までがつながります。一つの部門だけが良い仕事をしても、顧客に届く商品にはなりません。その部門間の依存関係と、最終的に商品として成立させる工程の厳しさを、開発の内側から学びました。

この経験は、AIの出力を見るときの基準になっています。もっともらしい回答や動作するコードが得られた後に、何を検証し、誰が判断し、どの条件で次へ進めるのか。成果物を作る能力と、成果物を受け入れる仕組みを、セットで考えるようになりました。

QCD / Quality gates / Cross-functional orchestration / Release readiness

Cognitive Guildへの接続

作成者とレビュー担当を分ける。品質条件をテストやチェックに落とす。変更と判断の証拠を残す。異常が起きたら見える形で失敗させる。これらを、人の注意力だけに頼らない運営の土台にしています。[1]

持ち込んだのは商品開発で得た規律と判断基準であり、現行システムが当社の全品質審査や認証を通過したという意味ではありません。

03 / OPERATING DISCIPLINE

不確実な仕事を、任せられる形にする。

次の土台は、米国のSaaS開発組織での活動です。Scrumの開発プロセスだけでなく、採用、オンボーディング、評価、そしてレイオフを含む退出のプロセスまで経験しました。人材が加わってから組織を離れるまで、役割と権限と責任がどう設計され、引き継がれるかを学びました。

Scrumで印象に残ったのは、手順の名前よりも、不確実性への向き合い方でした。最初からすべてを予測する代わりに、短い単位で実行し、結果を観測し、次の判断を変える。進捗の報告だけでなく、前提の誤りを発見できるプロセスにします。

しかも、実際の開発は一案件が左から右へ流れるだけではありません。あるテーマを顧客と発見している間に、別のテーマは解決策を設計し、次のリリースは計画され、現在のスプリントは実装と検証を進めます。ステージごとに関わる人と通過条件を変えながら、組織全体は同時並行で動き続けます。

その原則はAI組織にも生きます。何を任せるか、どこまで決めてよいか、何をもって完了とするか、判断に迷ったとき誰へ戻すか。Agentに専門家らしい名前を与えることより、その条件を明示することの方が重要です。

ただし、人間の組織図やScrumの儀式をそのままコピーするつもりはありません。実行の単位や速度が変われば、必要な分業やレビューの頻度も変わります。引き継ぐのは検査・適応・責任の原則であり、人間の工数制約に合わせてできた手続きは見直します。これは現行のMVVにも明記しています。[2]

Hiring & onboarding / Empirical process / Decision rights / Accountability

Cognitive Guildへの接続

職務と能力の要件、担当する仕事、権限境界、評価と記録を揃えます。採用ラウンドの記録には、担当範囲、既存の役割との境界、予算、登録と稼働開始の違いまで残します。「定義を作った」と「実際に動いた」を混同しません。[3]

04 / VALUE DISCIPLINE

仕事が終わった後、組織に何が残るのか。

三つ目の土台は、SaaS事業の売却を担った経験です。開発する側として見てきた事業を、金融・資本市場の視点から見直すことになりました。

そこで得た大きな転換は、現在のプロダクトや売上だけでなく、組織や事業が蓄積すべき資産に目を向けることでした。財務数値と、その背後にある顧客との関係、知的財産、プロセス、組織能力。有形のものだけでなく、目に見えにくい蓄積も含めて事業を見ます。

赤字、あるいは売上がまだない段階でも、なぜSaaS企業に投資する判断があり得るのか。この問いから私が持ち帰ったのは、足元の成果だけを数えるのではなく、将来の成果を繰り返し生むモデルと仕組みを見る姿勢でした。もちろん、仕組みがあれば資金調達や成長が保証されるわけではありません。ここで語りたいのは投資条件の一般解ではなく、開発者として自分の評価軸が変わったことです。

単利では、毎回の仕事が同じ元手に成果を足します。複利では、前回までに得た成果が次の仕事の元手に組み込まれます。差を生むのはAIの出力速度そのものではなく、手順、判断基準、評価方法、失敗からの教訓を再利用可能な形で残し、次の実行がそれを実際に使うことです。

AI組織には、この視点を持ち込んでいます。一つの仕事を終えるたび、回答だけが残るのか。それとも、次の仕事の品質と速度を変える資産が残るのか。何を蓄積し、どこで再利用し、効果をどう確かめるかを先に設計することで、実行を一回限りの消費で終わらせません。

Enterprise value / Intangible assets / Repeatability / Compounding capability

Cognitive Guildへの接続

Skillとして再利用する手順、実行履歴から抽出する意味のある記憶、判断を改善する評価基準、同じ失敗を防ぐ機械チェックを残します。能力を蓄積する対象と、次の実行で使う経路を、別々ではなく一緒に設計しています。[5]

AIでは、こうした知識を明示的に保存し、次の仕事へ渡す経路を作れます。しかし、誤った教訓を蓄積すれば、誤りも複利的に広がります。だからCognitive Guildでは記憶の更新も一つの仕事として扱い、根拠、更新権限、監査、劣化防止の条件を設けています。保存量ではなく、正しい学習が次の実行を変えたかを見ます。

05 / AN OPERATING ORGANIZATION

創業後、増やしたのは人数よりも、学習の閉じ方です。

Cognitive Guildを説明するとき、Agentの人数だけを実績にはしたくありません。役割が定義され、仕事が実行され、結果が確かめられ、その経験が次へ戻ること。その接続を、公開リポジトリの実装と記録からたどれるようにしています。

構築履歴を見ると、進化の方向は「より賢いAgentを増やす」から「組織が自分の失敗を見つけ、次の制度へ変える」へ移っています。月次レポートも成果広報ではなく、組織自身の診断装置として使っています。レポートの自己評価と、GitHubに残る実装済みの変更は分けて確認できます。

設計意図と、それを支える確認可能な仕組み
設計意図実装・記録組織としての意味
能力を定義するJD、役割境界、予算、登録手順を含む採用ラウンド記録 [3]必要な能力と任せる範囲を、稼働前に明らかにします。
任せ方を統治するAgent設定をDynamoDBへ集約し、APIで検証・変更履歴を記録 [6]誰が何を変えたかを追え、設定の二重管理を防ぎます。
成果を検証するPRレビュー、合意判定、CIと変更対象を再確認するマージ処理 [4]生成した本人の「できた」だけでは、変更を通しません。
経験を次へ渡す全案件の記録から意味記憶を更新する仕組み、古い記憶から対象を選ぶ処理 [5]一つの案件で得た教訓を、別の案件の判断にも使います。
同じ失敗を防ぐ再発記録を機械チェックへ昇格させるルールと、受容するリスクの台帳 [7]「次は気をつける」を、検出できる条件へ変えます。
活動を確かめるPR・リポジトリ指標の更新と、鮮度・欠損を確認する処理 [8]仕事が止まった状態と、順調に動いている状態を区別します。

実例：失敗を記録する仕組み自体を、改善する。

2026年9月4日にマージされたPR #652は、実行準備で失敗した際に実行台帳へ記録が残らない経路を修正したものです。開発担当AgentのRenによる変更として、関連Issue、修正内容、テスト、実環境では未確認の点まで記載されています。

これは失敗しない組織の証拠ではありません。失敗を発見し、修正し、観測できる範囲を広げる仕事が、実際に組織の中で行われている証拠です。[9]

改善の対象はコードだけではありません。Gitと実行時データの二重管理で設定反映が漏れた経験は、Agent設定の正本を一本化する設計へつながりました。記録を残しても教訓が次の仕事に届かなかった問題は、意味記憶を毎回の実行へ読み込む設計へつながりました。8月の自己評価では、自動マージ率6.9%、人間へ渡した理由の約4分の3が未分類という計測不全も報告されています。9月には、58名まで増えた後の増員を意図的に減速し、仕事の配属と「修正が本当に閉じたか」の確認を優先したと報告しています。[12] [13]

最初から完成形があったのではありません。失敗を見つけたことを成果とせず、その診断が制度やコードの変更として閉じ、次の実行を変えるところまでを組織開発として扱っています。これが、Cognitive Guildの創業後に見つけた進化の仕方です。

06 / WHY A GUILD

一つの仕事を終えるたび、次の仕事を担う力が残る。

Cognitive Guildという名前には、専門性の異なる担い手が仕事に集まり、成果を届け、経験を持ち帰る組織という意味を込めています。案件の編成は変わっても、役割、仕事の記録、学んだ判断は残ります。既存のマニフェストにある「Assemble, deliver, disband」は、その考え方を表しています。

量産商品開発からは、品質を工程で成立させる視点。米国SaaSの組織運営からは、不確実性の中で仕事を任せ、学び直す視点。事業売却からは、将来の成果を生む仕組みを資産として見る視点。この三つが、何をAIに任せ、何を検証し、何を残すかの判断軸になっています。

目指しているのは、人間の責任を消すことではありません。人間が目的と重要な判断を持ち続けながら、それを実行できる能力を、少しずつ組織の中に増やしていくことです。

成果を届ける。仕事を統治する。能力を蓄積する。
Cognitive Guildは、その三つを同時に実装する試みです。
