01Summary

要約と健全性ボード

asp-cloud は、カリフォルニアの約 25 世帯が参加する動的料金パイロット（製品名 CHARGE）のクラウド側です。家庭の蓄電池・電力センサ・給湯器・EV 充電器から測定値を集め、電力会社の価格信号に合わせて機器を制御し、運用者と参加者に画面と週次レポートを出します。憲法（L0）は ①接続が閉じる → ②運用が回る → ③生活を壊さない の順で、最適化・スケール・完全自動化は後回しと定めています。

機械的に数えた値 GitHub REST・git・workforce 台帳から 2026-10-10 に取得。10 月は 1〜10 日の部分月。

なぜ今この診断が要るか

4 月以降、開発体制は「1 人で直接 push」から「58 体 + 1 人、PR と週次監査で回す」に変わりました。半年で PR 番号は 1,000 を超えましたが、同じ期間に PR の待ち時間は中央値で約 4.5 倍、手戻り率は約 2.5 倍になり、信頼性指標（SLI-1）は W40〜W41 で Red に戻りました。スループットは維持されたのに、速度と安定性は改善していません。この構造のまま次の施工ラッシュ（24 世帯分）を迎えると、現場起因の不具合の修正が人の承認待ちで数日止まります（10）。

承認・マージ・配線・現地作業のすべてが 1 人に集まり、その人の処理能力を超えた分がキューの長さになっている。エージェントも監査も増やしたが、増えた分はこのキューに流れ込んだ。

次の 6〜8 週間で試す 3 件（09 に詳細）

改善 1

人のキューを細くする

author レーンの worker を配線し、非 L0/L1 で全員 🟢 の PR を人のキューから外し、hand-off を日次 digest にまとめる。🔴 を上書きしたマージには理由を 1 行残す。

改善 2

形骸化したゲートを実効化する

restapi lint の || true を外し、pip-audit を動く状態に戻し、カバレッジ floor を実測に合わせる。必須チェックは ADR 改正提案（L1）として出す。

改善 3

成果の物差しを 1 つにする

週報の冒頭に「価値の 1 行」、SLI-1 の raw 併記、lane マージ数の単一定義、Epic/ADR 状態ドリフトの CI 検査。

読み取り

  • パイプラインは律速ではない。merge → 本番は p50 1.5 分、p90 2.4 分。deploy path を触った 212 本すべてが最終的にデプロイされ、24 時間を超えた 10 本はすべて「デプロイ失敗の放置」か「ワークフロー未整備」でした。
  • 待ちは人のハンドオフに集中している。8 月以降、autopilot:needs-human 付き 105 本は p50 15.3h / p90 80.5h、なし 143 本は p50 0.8h / p90 7.3h。約 19 倍の差です。
  • デプロイは平準化した。5 月は 87 回が 10 日に集中、9 月は 69 回が 23 日に分散しています。
  • 変更失敗率は横ばい、本番の安定性は改善せず。SLI-1 は W40 で 87.58%（budget 消費 248%）。Sev-2 / Sev-3 とも自動アラームではなく人が検知しました（約 4 時間 / 約 8 日）。
  • 「休眠失敗」が最長の回復時間を作った。grafana-cloud は 06-09 の失敗が、path filter に掛かる変更が来るまで 76 日間誰にも再実行されず、08-24 に 10 連続失敗として再表面化しました。失敗した main デプロイを open のまま追う仕組みがありません。
  • 手戻りは倍増した。08-25 の 1 日で 23 本マージ、うち fix 15 本。本番でしか確認できない成果物（Grafana パネル、CFN スタック）を小 PR で出し、本番で直すループが常態化しています（仮説）。
  • 7 月の谷は供給の枯渇。W26（06-22 週）から PR 作成が週 6〜15 本に落ち、7 月に deploy path を触った PR は 8 本（全成功）。姉妹 repo も同時に 425 → 82 コミット。停止の記録はなく、原因は仮説です。

  1. refluster 名義には 3 主体が混在（人、オペレーターの Claude Code セッション、CCR 経由のペルソナ）。人手の判定は branch prefix・文体・cron 窓からの近似です。

  3. bot PR の CI run は「一度も実行されずに failure」と記録されていました（09-23 診断）。deploy-* には該当しないことを確認済みです。

  6. カバレッジ実測は単一 run のログ。ローカルでのテスト実行はしていません。
  7. fix / rework / 作業種別はヒューリスティック（タイトル正規表現 + 参照 + ファイル重複、キーワード分類 ±10%）。
