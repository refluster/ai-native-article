# Governance Mechanisms — the self-driving machinery

**Status:** v1.0
**Last updated:** 2026-06-07
**Scope:** the working mechanisms that make this repo's governance *run itself* — gates, registries, loops, hooks
**Audience:** any agent (or operator) who needs to operate, extend, or reason about the governance machinery

---

## 0. Why this doc exists

[`governance.md`](governance.md) is the **law** (what the rules are). [`design-policy.md`](design-policy.md)
is the **direction** (how we build). This doc is the **machinery**: the concrete mechanisms that
enforce the law and accelerate the work without the operator in the loop. It exists because the
two sibling repos this project learns from — **asp-cloud** (a layered legal code with a *converging*
audit loop) and **mononaware** (a heavy CI-gate platform with a *self-improving* feedback loop) —
solved two problems we had only solved on paper:

1. **Errors should get harder to make over time, automatically.** (mononaware's memory→lint pipeline.)
2. **Improvement work should be generated by signals, not by remembering to look.** (mononaware's
   Software 2.0 loop; asp-cloud's weekly audit cadence.)

We adopt the *mechanisms*, scaled to single-operator (C-3). We do **not** adopt the *ceremony*
(no SLO dashboards, no multi-stakeholder approval, no quarterly formal retro). The line between
"mechanism worth importing" and "ceremony to skip" is drawn explicitly in §5.

A new agent reads this doc to answer: *"what machinery already exists, and how do I operate or
extend it instead of reinventing it?"* — the anti-reinvention reflex, imported from mononaware.

## 1. The two engines

Everything below hangs off two engines. Learn these two and the rest is detail.

### Engine A — Errors get harder to make (the ratchet)

> A failure mode that bites twice is no longer a memory item — it's a missing check.

The mechanism is the **memory→lint backlog** ([`memory-lint-backlog.md`](memory-lint-backlog.md)):
every recurring failure is recorded; on its second occurrence within 90 days it is **promoted**
to a mechanical regulation (`R-NN` in governance.md §4). The seed case is the truncation incident
`d17e1d58ec42` → R-3/R-4/R-5 (runtime throws) → R-10 (pre-deploy gate). The backlog is the audit
trail that makes "why does this lint exist?" always answerable.

When a finding is real but **not** worth a machine check, it goes to the **risk-acceptance ledger**
([`risk-acceptance-ledger.md`](risk-acceptance-ledger.md)) instead — signed (= merged) by the
operator, suppressing re-litigation. Together the backlog and the ledger guarantee the audit loop
**converges**: every finding ends as promoted, accepted, or declined — never re-discovered from
scratch.

### Engine B — Improvement is generated, not remembered (the loop)

> Reader behaviour should drive the editorial roadmap, not die in a dashboard.

The mechanism is the **weekly content-insights loop**
([`weekly-content-insights.yml`](../.github/workflows/weekly-content-insights.yml) →
[`content-insights.mjs`](../scripts/content-insights.mjs)): GA4 engagement is joined to the
published manifest and the gaps/top-performers are upserted into a single `insights`-labelled
GitHub issue every Monday. The operator (or an agent) triages that issue into editorial action.
This is the article-side analogue of mononaware's `weekly-insights.yml` → `sw2-actionable` loop,
and the implementation of `design-policy.md` D-2 (Software 2.0).

### 2.1 How to operate each

- **R-10 corpus truncation** — runs automatically in `deploy-article-site.yml`. If it fails, an
  article is truncated *after a fresh Notion fetch*: fix the Notion row or run `L2_BACKFILL`, then
  redeploy. Emergency escape hatch (operator-only): `ALLOW_TRUNCATED=1` to ship an unrelated fix
  while regenerating; record it in the risk-acceptance ledger.
- **R-11 L1 citation** — runs on PRs. If you edit an L1 doc (governance.md §3.1 list, or
  governance/design-policy themselves), put in the PR body either a reference to the L1 doc you're
  changing, or `RULE-N/A: <reason>`. This is asp-cloud's R-15 (ADR-presence), scaled down.
- **R-12 registry integrity** — runs on PRs and at push (via the hook). Keeps the two registries
  parseable. If you add a column, update the `<!-- registry:… columns: … -->` anchor in the doc to
  match.
- **Content-insights** — inert until the operator provisions `GA4_PROPERTY_ID` + `GA4_SA_KEY`
  (RAL-002). Run a preview anytime: `DRY_RUN=1 npm run content-insights` (still inert without creds).
- **Local hooks** — install once per clone: `git config core.hooksPath .githooks`. Claude Code
  sessions should run this at session start.

## 4. Extending the machinery (anti-reinvention)

Before adding a new gate, loop, or registry, check this list — the mononaware lesson is that the
expensive mistake is building a *parallel* mechanism next to one that already exists.

- **New recurring failure mode?** → add a row to `memory-lint-backlog.md`. Do **not** write a
  one-off lint without a backlog row; the row is the provenance.
- **New mechanical check?** → add an `R-NN` row to governance.md §4 and a script under `scripts/`;
  wire it into `ci.yml` (PR-time) and, if fast+offline, `.githooks/pre-push`. Do **not** add a new
  workflow file for a single small check — fold it into `ci.yml` (asp-cloud's "fold into a sibling"
  convention).
- **New known-but-tolerated gap?** → add a row to `risk-acceptance-ledger.md`; an agent drafts, the
  operator signs by merging.
- **New analytics signal?** → extend `content-insights.mjs` and the single `insights` issue. Do
  **not** create a second dashboard or a second issue stream (mononaware's "single home" rule).
- **New scheduled automation?** → its output goes to a GitHub issue or a PR, never a direct push to
  `main`.

## 5. What we deliberately did NOT import (C-3 boundary)

Scaling-down is a design act. These are real mechanisms in the sibling repos that we judged to be
ceremony at single-operator scale. The reasoning is recorded so a future maintainer (post-growth)
knows what to turn on, not just what's off.

| Not imported | From | Why not (revisit when…) |
|---|---|---|
| SLO + error-budget throttle | asp-cloud / mononaware | No SLA, no users to budget against. Revisit if the site takes payments or hosts user data. |
| Reviewer-disposition gate | mononaware | No second reviewer — single operator merges. Revisit at multi-author. |
| 20+ required CI gates with a single router | mononaware | Overkill for ~3 gates; a flat list in `ci.yml` is clearer. Revisit past ~10 gates. |
| Three-registry boundary (Agent/Accountability/Skill) | mononaware | Article side has one operator; workforce side already separates concerns. |
| Formal quarterly retro with output doc | asp-cloud | Replaced by the incident-driven §6 loop + the memory-lint backlog. |
| RFC process before L1 change | both | The L1 citation gate + operator approval is enough at this scale. |

The discipline: **import the mechanism, not the ceremony.** When in doubt, the lighter option wins
(D-1), but the heavier version is one merge away and its provenance is one click away.
