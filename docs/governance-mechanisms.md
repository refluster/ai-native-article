# Governance Mechanisms — the self-driving machinery

**Status:** v1.1
**Last updated:** 2026-07-03
**Scope:** the working mechanisms that make this repo's governance *run itself* — gates, registries, loops
**Audience:** any agent (or operator) who needs to operate, extend, or reason about the governance machinery
**Decision record:** [ADR-0001](adr/adr-0001-self-driving-governance-mechanisms.md)

---

## 0. Why this doc exists

[`governance.md`](governance.md) is the **law** (what the rules are). [`design-policy.md`](design-policy.md)
is the **direction** (how we build). This doc is the **machinery**: the concrete mechanisms that
enforce the law and accelerate the work without the operator in the loop. The *decision* to adopt
them — and what was deliberately left out — is recorded in
[ADR-0001](adr/adr-0001-self-driving-governance-mechanisms.md); this doc is the *operating map*.

Two gaps drove it, both felt concretely on this repo:

1. **Errors should get harder to make over time, automatically** — the truncation incident
   `d17e1d58ec42` was fixed by hand but the *class* of failure wasn't recorded, so a second
   occurrence would be re-discovered from scratch.
2. **Improvement work should be generated by signals, not by remembering to look** — GA4 was wired
   on the client but the data never came back to drive the editorial roadmap.

We adopt the *mechanisms*, scaled to single-operator (C-3). We do **not** adopt the *ceremony* (no
SLO dashboards, no multi-stakeholder approval, no quarterly formal retro). The line between
"mechanism worth keeping" and "ceremony to skip" is drawn explicitly in §5 and ratified in ADR-0001.

A new agent reads this doc to answer: *"what machinery already exists, and how do I operate or
extend it instead of reinventing it?"*

## 1. The two engines

Everything below hangs off two engines. Learn these two and the rest is detail.

### Engine A — Errors get harder to make (the ratchet)

> A failure mode that bites twice is no longer a memory item — it's a missing check.

The mechanism is the **memory→lint backlog** ([`memory-lint-backlog.md`](memory-lint-backlog.md)):
every recurring failure is recorded; on its second occurrence within 90 days it is **promoted**
to a mechanical regulation (`R-NN` in governance.md §4). The seed case is the truncation incident
`d17e1d58ec42` → R-3/R-4/R-5 (runtime throws) → R-10 (pre-deploy gate). The backlog is the audit
trail that makes "why does this lint exist?" always answerable.

When a finding is real but **not** worth a machine check, it goes to the **risk-acceptance ledger**
([`risk-acceptance-ledger.md`](risk-acceptance-ledger.md)) instead — signed (= merged) by the
operator, suppressing re-litigation. Together the backlog and the ledger guarantee the audit loop
**converges**: every finding ends as promoted, accepted, or declined — never re-discovered from
scratch.

### Engine B — Improvement is generated, not remembered (the loop)

> Reader behaviour should drive the editorial roadmap, not die in a dashboard.

The mechanism is the **weekly content-insights loop**
([`weekly-content-insights.yml`](../.github/workflows/weekly-content-insights.yml) →
[`content-insights.mjs`](../scripts/content-insights.mjs)): GA4 engagement is joined to the
published manifest and the gaps/top-performers are upserted into a single `insights`-labelled
GitHub issue every Monday. The operator (or an agent) triages that issue into editorial action.
This implements `design-policy.md` D-2 (Software 2.0).

### 2.1 How to operate each

- **R-10 corpus truncation** — runs automatically in `deploy-article-site.yml`. If it fails, an
  article is truncated *after a fresh Notion fetch*: fix the Notion row or re-run the relevant
  workforce cadence (`article-level{2,3}`), then redeploy. Emergency escape hatch (operator-only):
  `ALLOW_TRUNCATED=1` to ship an unrelated fix while regenerating; record it in the risk-acceptance
  ledger.
- **R-11 L1 citation** — runs on PRs. If you edit an L1 doc (governance.md §3.1 list, the two
  governance-axis docs, or any ADR under `docs/adr/`), put in the PR body either a reference to the
  doc you're changing, or `RULE-N/A: <reason>`. This is how "follow the ADR when implementing" is
  enforced: touching a law announces itself.
- **R-12 registry integrity** — runs on PRs. Keeps the two registries parseable. If you add a
  column, update the `<!-- registry:… columns: … -->` anchor in the doc to match.
- **CloudFormation/SAM lint** — runs on every PR as a step of the `ci.yml` `check` job (folded into
  a sibling rather than given its own workflow). It lints every `template.yaml` under
  `workforce/infra/` with a pinned `cfn-lint`, and `--non-zero-exit-code error` keeps it red only on
  error-class findings — the EarlyValidation class that previously failed at deploy time (#391's
  CloudFront `Tags` placement, and the duplicate `PointInTimeRecoverySpecification` key this gate
  caught on its first run). Warnings and informational findings do not fail the build, so the gate
  stays about "would this deploy have blown up", not template style. Reproduce locally with
  `pipx run cfn-lint==1.53.3 --non-zero-exit-code error -- $(find workforce/infra -name template.yaml)`.
  Not yet a numbered R-rule: the statute row is an L1 edit, proposed for operator sign-off (ML-023),
  and the mechanical check does not wait on it.
- **Content-insights** — inert until the operator provisions `GA4_PROPERTY_ID` + `GA4_SA_KEY`
  (RAL-002). Run a preview anytime: `DRY_RUN=1 npm run content-insights` (still inert without creds).
- **R-13 terminal-state sweep** — runs daily via `workforce-pr-terminal-sweep.yml` with `--apply`:
  any open PR the autopilot left in a non-terminal state (an unlabelled hand-off, a stalled review
  cycle, a PR aged out of the discovery window) is escalated — labelled `autopilot:needs-human`
  (plus a hand-off comment for the stale classes). Check-only anywhere:
  `GITHUB_TOKEN=… npm run workforce:pr-sweep -- --repo <owner>/<repo>` (exit 2 = violations).
  Promoted from ML-009 per the §6.1 ratchet; the ML-009 state check
  (`npm run workforce:escalation-labels`) remains the narrow marker-vs-label lint.

## 3. The decision record

The rationale for every mechanism here — and the explicit list of what was deliberately *not*
adopted — lives in [ADR-0001](adr/adr-0001-self-driving-governance-mechanisms.md). The point of
keeping it in an ADR (rather than folklore) is that when one of these mechanisms feels wrong, the
context that justified it, the alternatives rejected, and the scope boundary are all in one
append-only record. If you reverse one of these decisions, supersede ADR-0001 with a new ADR —
don't quietly edit it.

Each mechanism maps to the problem it solves:

| Mechanism | Problem it solves |
|---|---|
| Layered law L0–L3, action-authority A/B | "Which rules constrain which, and what may an agent do without asking?" |
| L1 citation gate (R-11) | A framework-law edit could ship without announcing which law it touched. |
| Risk-acceptance ledger | Known-but-tolerated gaps were re-litigated every retrospective. |
| Converging audit loop (promote / accept / decline) | The audit backlog could grow without ever closing. |
| Memory→lint promotion backlog | A failure that bit twice was re-discovered, not mechanised. |
| Content-insights (analytics→issue) loop | Reader data died in a dashboard instead of driving the roadmap. |
| Pre-publish health gate (R-10) | The generation-time W-1 guard (historically the GAS finish_reason throw) guards generation, not publication. |
| ADRs as the decision-record vehicle | Architectural rationale lived in chat history, not the repo. |

## 4. Extending the machinery (anti-reinvention)

Before adding a new gate, loop, or registry, check this list — the expensive mistake is building a
*parallel* mechanism next to one that already exists.

- **New recurring failure mode?** → add a row to `memory-lint-backlog.md`. Do **not** write a
  one-off lint without a backlog row; the row is the provenance.
- **New mechanical check?** → add an `R-NN` row to governance.md §4 and a script under `scripts/`;
  wire it into `ci.yml`. Do **not** add a new workflow file for a single small check — fold it into
  `ci.yml`.
- **New framework decision?** → write an ADR under `docs/adr/`. Implementation then cites it (R-11).
- **New known-but-tolerated gap?** → add a row to `risk-acceptance-ledger.md`; an agent drafts, the
  operator signs by merging.
- **New analytics signal?** → extend `content-insights.mjs` and the single `insights` issue. Do
  **not** create a second dashboard or a second issue stream.
- **New scheduled automation?** → its output goes to a GitHub issue or a PR, never a direct push to
  `main`.

## 5. What we deliberately did NOT adopt (C-3 boundary)

Scaling-down is a design act. These are real mechanisms in heavier governance frameworks that we
judged to be ceremony at single-operator scale. The reasoning is recorded so a future maintainer
(post-growth) knows what to turn on, not just what's off. This table is ratified in
[ADR-0001 → Consequences](adr/adr-0001-self-driving-governance-mechanisms.md#consequences).

| Not adopted | Why not (revisit when…) |
|---|---|
| SLO + error-budget throttle | No SLA, no users to budget against. Revisit if the site takes payments or hosts user data. |
| Reviewer-disposition gate | No second reviewer — single operator merges. Revisit at multi-author. |
| A single required-gate router over many gates | Overkill for ~3 gates; a flat list in `ci.yml` is clearer. Revisit past ~10 gates. |
| A separate Agent/Accountability/Skill registry boundary | Article side has one operator; the workforce side already separates concerns. |
| Formal quarterly retro with output doc | Replaced by the incident-driven §6 loop + the memory-lint backlog. |
| A local `git push` hook mirror | Removed at review — CI is the single enforcement point. |

The discipline: **keep the mechanism, not the ceremony.** When in doubt, the lighter option wins
(D-1); the heavier version is one ADR away and its rationale is one click away.
